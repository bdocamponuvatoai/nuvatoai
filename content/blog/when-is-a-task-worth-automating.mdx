A task is worth automating when it repeats often, follows the same steps each time, and causes real trouble when it is late or done wrong. If the steps change every time, or the task needs a judgment call at each turn, fix the process first, because automating a messy process makes the mess happen faster.

This post is for owners of businesses of about ten to twenty people in the US, Canada and Argentina. Each section stands on its own, so read the one you need.

## What makes a task a good fit for automation?

Look at one task you or your team did this week and ask four questions about it.

1. **Does it repeat?** A task that happens every day or every week is a better candidate than one that happens twice a year.
2. **Are the steps the same each time?** If two people would do it the same way, the steps can be written down. If each person does it their own way, they can't be automated yet.
3. **Does it start from something you can see?** A form arrives, an invoice is paid, a date passes. Automation needs a clear trigger to begin.
4. **Does it hurt when it is missed?** A follow-up that never goes out, a record copied with a typo, a reminder nobody sent. The cost of a mistake is part of the case.

A task that gets four yes answers is a strong candidate. One that gets two is usually better served by a written procedure for now.

## What makes a task a bad fit?

Some tasks look repetitive but are not ready, or not right, for automation.

- **The steps change every time.** If the work depends on who the customer is and what they said, a person is doing judgment work, not routine work.
- **It happens rarely.** Building and looking after an automation takes effort. A task that comes up a few times a year rarely repays it.
- **Nobody agrees how it should be done.** If your team would describe the task three different ways, automating any one version locks in a guess.
- **A mistake would be hard to undo.** Sending money, deleting records or making a promise to a customer should keep a person in the loop, even when the steps are routine.
- **The real problem is somewhere else.** If enquiries sit for days because nobody owns the inbox, an automation will not fix that. Deciding who owns it will.

## Should you write the process down before you automate it?

Yes. Writing it down is the cheapest test there is.

Ask the person who does the task to write each step on one page, in order, as it is done today. Then read it with them. You will find out three things fast: whether the steps are actually the same each time, where the decisions are, and where things wait for someone.

That page is a standard operating procedure, or SOP. If you have never written one, our guide on [what an SOP is and when a small business needs one](https://nuvato.ai/blog/what-is-an-sop) walks through it.

Often the written page fixes most of the problem on its own. People stop skipping steps once the steps are visible. When it doesn't, the page becomes the brief for the automation, so nothing is built on a guess.

## How do you weigh the time a task takes against the cost of automating it?

There is no fixed number of minutes that makes a task worth automating. What matters is the whole picture, so put these side by side:

| Ask about the task | Ask about the automation |
|---|---|
| How often does it happen? | What does it cost to build? |
| How long does it take each time? | Who looks after it when something changes? |
| What happens when it is late or wrong? | What does a person still need to check? |
| Who has to stop other work to do it? | How will you know if it stops working? |

A short task that happens many times a day can be worth more than a long one that happens once a month. A task where one mistake costs a customer can be worth automating even if it is quick.

Be honest about the right-hand column. An automation is not finished when it is built. Tools change, forms change, people leave. Someone has to own it, the same way someone owns any other part of the business.

## What should you automate first?

Start with the task that got the most yes answers above and has one clear owner. Write it down, run it from the page for a couple of weeks, and fix what the page shows you. Then decide whether it still needs automating.

## Common questions

### How much time does a task need to take before automating it pays off?

There is no single number. Weigh how often the task happens, how long it takes each time and what a mistake costs, against what the automation costs to build and look after. A quick task that repeats many times a day, or one where errors reach customers, can be worth it before a long but rare one.

### What makes a task a bad fit for automation?

A task is a poor fit when its steps change every time, when it happens rarely, when your team does not agree on how it should be done, or when a mistake would be hard to undo. If the real problem is that nobody owns the work, an automation will not fix it.

### Should you write the process down before you automate it?

Yes. A one-page SOP, written by the person who does the task, shows whether the steps are really the same each time and where the decisions sit. It often fixes the problem on its own, and when it does not, it becomes the brief for the automation.
